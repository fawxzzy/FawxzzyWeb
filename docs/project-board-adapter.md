# Owner-only project boards

Decision (Zac, 2026-11-13): Projects is for the account owner only. Signed-out visitors and every other account see no Projects tab and no cards, so there is no per-card hiding, approval list or text screen any more. The earlier public model (an owner-approved allowlist, a sensitive-text screen, an exclusion list and a separate private-card reader) was removed.

## How it works

1. **Nav tab.** `SiteNav` renders no Projects link in the static HTML. `OwnerProjectsLink` (client) asks `GET /api/projects/access` with the signed-in Auth bearer and shows the tab only when the server answers `{ "owner": true }`. Signed-out visitors make no request. The main site (`fawxzzy.com`) has no Auth session, so it never shows the tab; the owner uses `https://account.fawxzzy.com/projects`.
2. **Page.** `/projects` is a static, `noindex` shell with no board data (`OwnerProjectBoard`). After the browser Auth session is verified it fetches `GET /api/projects/board`, validates the snapshot through the board adapter (`buildOwnerBoardState`) and renders `ProjectBoard`. Signed out: a plain sign-in link (`/login?returnTo=%2Fprojects`). Signed in as another account, or any error: one neutral "not available for this account" message. Off the account origin the page is only a sign-in link to the account origin.
3. **Server.** `api/projects/access.ts` and `api/projects/board.ts` delegate to `src/server/projects/owner-projects-http.mjs`. Each request must be same-origin on `https://account.fawxzzy.com` with fetch metadata and the `X-Fawxzzy-Projects: 1` marker, a Supabase bearer that the master Auth service accepts (`authenticate` in `src/server/operations/consumer-auth.mjs`), and a subject equal to the server-only `OPERATIONS_OWNER_SUBJECT` UUID. A missing or malformed setting fails closed for everyone. Non-owners get the same opaque 403; outages get 503; both are `private, no-store`.
4. **Data.** `src/server/projects/owner-board.generated.mjs` holds every card of every listed source. It lives under `src/server/` and is imported only by the board function, so it is never part of the static site; `tests/project-board-owner-snapshot.test.mjs` fails if client or static code references it. Do not move it under `src/data/` or `public/`.

Without `OPERATIONS_OWNER_SUBJECT` on the account deployment, nobody (including the owner) sees the tab or the boards. Setting it is a production environment change that needs Zac's approval.

## Refreshing the boards

1. Copy the new owner export into `planning/board-sources/` (or regenerate `exports/trove.project-board.owner-export.v1.json` with `npm run data:project-board-owner` for the Web board). The sources and their board mapping are listed in `planning/project-board-sources.v1.json`.
2. `npm run data:project-board-owner-snapshot` regenerates the snapshot; `npm run data:project-board-owner-snapshot:check` (part of `npm run test:project-board-preview` and `npm run verify`) fails if the committed file is stale. There is nothing to approve per card: every card in a listed source is shown. A new source needs one manifest entry.
3. The generator keeps the adapter's fields: id, title, summary, lifecycle, updatedAt, source project, source revision, plus fixed `owner`, `workType`, `component` (Atlas Stack only), `dependencies` and null `priority`, `parentId`, `duplicateOf`, `supersededBy`. Evidence, blockers, acceptance criteria, next actions and source references are not copied. A dependency is kept only when its target card is in the snapshot (the adapter requires every link to resolve); others are dropped and counted in the generator output.
4. The repository is public, so the committed owner exports in `planning/board-sources/` and `exports/` are readable on GitHub whatever this page does. Keep private-only material out of owner exports.

Snapshot cards carry their source `updatedAt` dates and the snapshot states its source date range and that it is not live. Visual-regression baselines do not include `/projects`.

`src/data/project-board-adapter.mjs` validates the board snapshot the owner endpoint returns: exact board and card fields, source identity, revisions, real calendar dates, scalar string fields, generation time, publication readiness, and health. A validated healthy nonempty snapshot is advanced through `applyBoardEnvelope` and rendered. Exact repeats are idempotent. Forked or backdated revisions show last accepted data as non-authoritative. Invalid, incompatible, and unavailable responses expose no cards. The empty placeholder is accepted only as an unapproved initial state; it cannot become a healthy projection. (Some adapter names and the `fawxzzy.project-board.public-preview.v1` schema string predate the owner-only decision and are kept so the contract does not change.)

The repository has no live card transport, polling loop, board writer, reverse editor, or database client for this view; the former inactive public HTTP reader seam was removed on 2026-11-13. The adapter's envelope is not an adopted platform API. Test-only synthetic cards exercise status changes, relationships, field rejection, and detail selection; they are not current project work.

The adapter requires `previousRevision` to match the last accepted revision. A cold client at `projectionRevision: null` cannot accept a latest-only envelope with `previousRevision: r2`; a client at `r1` cannot accept `r3` with `previousRevision: r2`. Both remain reconciling. A future live source must adopt sanitized response, identity, bootstrap and missed-revision recovery semantics before it replaces the committed snapshot.
