# Public project-board source boundary

`/projects` provides the four requested display boards: Fitness, Mazer, Fawxzzy Web, and Atlas Stack. The cold-start JSON `project-board-preview.generated.json` is an empty, dated placeholder with `publicationReady: false`; the page replaces it with the owner-approved snapshot described below, and is excluded from search indexing.

## Published public snapshot (runbook)

Status: `/projects` now renders owner-approved, already-public roadmap and backlog cards from `src/data/project-board-public.generated.json` (`publicationReady: true`). `src/components/projects/public-project-board.tsx` passes that snapshot through `buildPublicBoardState` (`src/data/project-board-public-state.mjs`), which applies it with `applyBoardEnvelope` as a first healthy envelope when the bundle is built and prerendered. There is still no fetch, endpoint, provider, or environment variable; the empty `project-board-preview.generated.json` remains the cold-start state and a rejected snapshot fails the build. Private cards: the signed-in owner section reports that private project cards are not available yet unless the account-origin reader returns the first accepted card (`FW-ANALYTICS-001` as `FF-WEB-ANALYTICS-001`, board `fawxzzyweb`). That card is a client-only read of `/api/projects/private-card`; the card region renders nothing at all while loading, when the reader RPC is not installed, for any non-owner, and on any mismatch of subject, grant epoch, body digest, board, board revision or source revision, so the page is then identical to the page without the card.

How a card becomes public ("approved"):

1. Inputs are committed copies of the owner exports in `planning/board-sources/` (Atlas, Cortex, Foundation, Lifeline, Stack, Playbook, Fitness, Mazer; plus the Web export already in `exports/`). Each is pinned by sha256 in `planning/project-board-public-allowlist.v1.json`. To refresh a source, copy the new owner export in and update its pin; the build refuses an unpinned or edited source.
2. Approval is the `include` list in `planning/project-board-public-allowlist.v1.json`, keyed by source project. A card is public only if its id is listed there. Merging a change to that file (a normal reviewed PR) is the owner approval. Every card in a pinned source must be either in `include` or in `exclude` with a reason; the test fails on an unreviewed card, so new upstream cards never appear by themselves.
3. `npm run data:project-board-public` regenerates the snapshot; `npm run data:project-board-public:check` (part of `npm run test:project-board-preview` and therefore `npm run verify`) fails if the committed file is stale.
4. The generator publishes only the adapter's fields: id, title, summary, lifecycle, updatedAt, source project, source revision, plus fixed `owner` (the source project), `workType`, `component` (Atlas Stack only), an empty-or-in-snapshot `dependencies` list, and null `priority`, `parentId`, `duplicateOf`, `supersededBy`. Evidence, blockers, acceptance criteria, next actions, source references, and any path are never copied. Dependencies on cards that are not published are dropped. A title or summary that looks like a path, file name, URL, email, token, secret, credential, security finding, payment or monetization text, personal data, or an excluded program stops the build instead of being silently scrubbed.
5. `exclude` is the explicit never-public list. Currently excluded by default: `FW-ANALYTICS-001` (`public_safe:false`); the Atlas lanes about secrets, security, Supabase advisor, Vercel/Supabase monitoring, Dependabot, CreationOS, Stream, DiscordOS, and local branch/worktree inventories; and the Fitness monetization and launch cards `FF-MKT-001`, `FF-BETA-001`, `FF-ANALYTICS-002` (plus `FF-SOC-001`, whose summary mentions the paid product). The monetization cards stay out until the owner decides their timing; adding one is an allowlist edit plus removing it from `exclude`. The Playbook source (`playbook`, shown under the Atlas Stack tab as the Playbook group) is the repository's own roadmap export; its commercial packaging and design-partner rollout cards stay out, and its delivery-system card was withheld until the owner roadmap text was reworded to pass the public-text screen (now published).

Snapshot cards carry their source `updatedAt` dates, and the source exports predate today; the snapshot states its source date range and that it is not live. Visual-regression baselines do not include `/projects`, so no baseline change is needed.

`src/data/project-board-adapter.mjs` is a local source seam for a future authorized public projection. It validates exact board and card fields, source identity, revisions, real calendar dates, scalar string fields, generation time, publication readiness, and health. A validated healthy nonempty snapshot can be supplied to the renderer by an eventual approved caller. Exact repeats are idempotent. Forked or backdated revisions show last accepted data as non-authoritative. Invalid, incompatible, and unavailable responses expose no cards. The empty placeholder is accepted only as an unapproved initial preview; it cannot become a healthy public projection.

`src/data/project-board-public-read.mjs` is an inactive, one-shot HTTP reader source seam. `createPublicBoardReader(initialState)` is disabled and makes no request. An eventual approved caller must explicitly inject both a public URL and a fetch implementation, then call `refresh()`; this repository supplies neither a default URL nor a caller. A disabled configuration also makes zero requests. Each enabled read omits credentials, refuses redirects, requires a JSON 200 response, bounds response size and request time, and passes decoded envelopes to the existing adapter. Transport and decode failures hide cards while preserving the last accepted snapshot and freshness privately. Concurrent and late reads cannot replace a newer result. The local size and timeout bounds are source safety limits, not an adopted platform response contract.

Projects navigation stays visible without signing in and is origin-relative (`/projects`), so the public boards live on the main site (`https://fawxzzy.com/projects`, canonical there, `noindex`). The same static page is also served on the account origin, where it canonicalizes to the main site and is the owner's private view because the browser Auth session lives there. The page renders the public board shell and the existing private Operations observation in one place. On any non-account origin the private region is only a plain `Sign in to see private work` link to the account-origin login with the `/projects` return target; no reader, adapter, or request runs there. On the exact account origin, an already signed-in browser checks the private reader once; a definite missing-session denial may open one caller-bound session and read once. Uncertain responses do not retry or reveal cards. The private observation is client-only, short-lived, and never serialized into the public page HTML or public board snapshot. Signed-out users and other authenticated subjects receive no private cards. The private section does not invent canonical private board membership: the current Operations projection exposes cards without a board map. A protected owner-approved board mapping and installed reader remain needed for actual private board tabs. The former `/operations` path is only a static-export-compatible client redirect to `/projects`; it renders no separate work overview or private data.

The private server endpoint additionally requires a server-only `OPERATIONS_OWNER_SUBJECT` UUID matching the current master-verified Auth subject before touching the RPC. Missing or mismatched binding fails closed; local browser fixtures use dummy subjects. The existing Auth/session-bound RPC grant is still required. No provider setting or real account session is changed by this source. Only the protected owner may establish the actual subject binding, installed RPC/API exposure, login journey, and live acceptance.

The repository still has no active public projection transport, polling loop, board writer, reverse editor, or database client for this view. The adapter's envelope is not an adopted platform API. Test-only synthetic cards exercise status changes, relationships, privacy rejection, and detail selection; they are not current project work. Actual public fields and prose require their owners' approval before entering repository source. Private operator records stay with their canonical writer and must not be serialized into public HTML, public board snapshots, or shared caches.

The current adapter requires `previousRevision` to match the last accepted revision. A cold client at `projectionRevision: null` cannot accept a latest-only envelope with `previousRevision: r2`; a client at `r1` cannot accept `r3` with `previousRevision: r2`. Both remain reconciling. The canonical Platform owner must adopt sanitized public response, identity, bootstrap and missed-revision recovery semantics, the actual public URL or artifact, and refresh policy before this reader can be connected. The source does not bypass its stale/fork guard or assume a latest-snapshot read is sufficient. The existing card writer and one approved real card remain prerequisites for a source-to-page/result-return acceptance. Source publication, deployment, and that real-card acceptance are separate gates. The current source establishes UI, validation, and an inactive reader behavior only.
