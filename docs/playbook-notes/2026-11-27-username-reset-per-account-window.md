## 2026-11-27 - Per-account 65 s send window (reservation, released only on a recipient-independent refusal) for username password reset

- Type: Decision + Failure Mode fix (source only; SQL is proposed and owner-gated)
- WHAT changed: new proposed SQL `supabase/proposed/20261126190000_account_username_reset_v2.sql` (+ rollback, read-only preimage, pglite scratch test) adds `account_api.account_resolve_username_reset_v2` and `account_api.account_release_username_reset_v2`: a per-account 65 s send window in the existing `account_private.username_signin_attempts` table, claimed by a real send only and given back only when the provider refuses the call for a reason that does not depend on the recipient (captcha_failed, network error, provider not configured). The Edge Function handler answers 429 `{"code":"reset_wait"}` (Retry-After 1-65, exposed to the browser) with no provider call; the account portal counts down the server Retry-After. Test adapter adds `auth_test=reset-username-wait` (Retry-After 37).
- WHY it changed: the provider refuses a second recovery email inside one minute per account, silently. The only guard was client-side localStorage, so a repeat from a different browser said "sent" with no mail. The first version claimed the window before the provider validated the captcha and on decoys, so a caller with the public key and no captcha could keep one person on "wait" (review hold, PR 241); a late clock also produced a 61 s wait that the handler turned into a 503.
- Rule (round-2 review P2-b): release ONLY on refusals decided before the recipient matters (captcha failure error code, network error, provider not configured); KEEP the window on 2xx, 429, every other 4xx and every 5xx. A real address can fail at SMTP (4xx/5xx) while a decoy never reaches SMTP and answers 2xx, so releasing on those answers is an existence oracle for a second-IP probe, free while CAPTCHA is off. No client-side provider timeout either (a slow real SMTP send would be recipient-dependent).
- Rule (round-2 review P2-a): state the precondition of a protection next to the claim. The captcha-failure release only protects once provider CAPTCHA is enforced (FW-CAPTCHA-001, blocked, NOT enforced today); until then a captcha-less request is a real send, the window is kept and an attacker rotating about 7 addresses can hold the owner on "wait" (same exposure as v1's silent provider minute, not a regression). The go-live step that expects a released window is conditional on enforcement; with CAPTCHA off the expected result is the opposite (kept, 429 wait).
- Rule: a server window mirroring a provider limit must be a reservation: never claimed for a request that sends nothing (decoy), and released when the provider refuses the call, so an unauthenticated caller cannot hold it. Keep 429 (the provider's own limit) claimed, or the release becomes an existence oracle. Key it by hash of the account (name when unknown), identical for known and unknown usernames; a turned-away request neither extends the window nor spends the send cap.
- Rule: size a server window to the provider's window plus the head start of its clock (60 s + 5 s), and clamp computed waits to it in the database AND the caller.
- Failure Mode: relying on a client-only throttle for a limit the server and provider enforce; and claiming a server-side window before the downstream (captcha/provider) check has passed.
- Decision: additive v2 (v1 untouched) so apply-then-deploy and rollback-then-redeploy are each safe in order; waits are not counted in the pair counter; release runs in the background after the fixed answer, so callers cannot tell success from refusal.
- Evidence: `tests/username-password-reset.test.mjs` (35 pass: release pinned to captcha_failed/network/not-configured; known-address 4xx/5xx and decoy 2xx keep the window identically; `released` log field), `tests/e2e/account-reset-anybrowser.spec.ts`, scratch test `supabase/proposed/account_username_reset_v2.scratch-test.mjs` (122 checks pass incl. attacker with captcha_failed, SMTP-422 vs decoy oracle case, network-error release, decoy, late-clock, release and prod-vs-repo md5), preimage JSON (captured_at 2026-11-27 02:33:50 UTC) saved next to the SQL.
- Status: source only. SQL (unchanged this round, sha256 274bfe0b...a724) not applied and function not deployed; re-run the read-only preimage right before applying, apply the SQL (by sha256), then deploy the function.
